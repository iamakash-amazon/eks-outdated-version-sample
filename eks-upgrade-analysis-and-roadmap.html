Roadmap to Production

Everything you need to take the transformed code safely to production is on this tab — this is self-contained. EKS operates under a shared-responsibility model: AWS upgrades the control plane; you own the add-ons, the data plane, and validating that your workloads still run.

The upgrade order (and why)

Every environment follows the same ordered sequence — it comes from the EKS cluster-upgrade guidance and the version-skew policy.

  1. Assess readiness — Cluster Insights + deprecated-API scan. A removed API in use is rejected the moment the control plane advances — catch it before, not during.
  2. Fix the IaC (this transformation) — reviewable, repeatable across environments.
  3. Fix the workloads (app team + manual) — control-plane API removals and OS/cgroup changes break apps, not infra. Remediate before the API server changes underneath them.
  4. Upgrade the control plane — AWS-managed, reversible within 7 days, must lead the data plane.
  5. Upgrade the add-ons (VPC CNI, CoreDNS, kube-proxy, CSI) — NOT auto-upgraded; one minor at a time.
  6. Upgrade the data plane (nodes) to match — this is where AL2→AL2023 lands (Hop 3).
  7. Validate, then promote to the next environment.
ℹ️ Version-skew safety net: for Kubernetes ≥ 1.28, kubelet may trail the API server by up to 3 minor versions (n-3; n-2 below 1.28). That is what makes "control plane first, nodes after" safe — old nodes keep serving against the new control plane while you roll them. Hop 1 exception: nodes left at 1.24 behind a 1.31 control plane are already outside this window — roll them immediately.

Phases

  1. Phase 0 · Plan & assess — confirm the hop; run aws eks describe-cluster (control-plane version) and check node/kubelet versions; run Cluster Insights for upgrade readiness; read release notes; take a baseline/backup.
  2. Phase 1 · Set up a safe rollout path — the same change flows through Dev → UAT/Staging → Production; never upgrade prod first.
  3. Phase 2 · Upgrade the IaC — apply the reviewed diff; confirm the plan is in-place, not destroy/recreate.
  4. Phase 3 · Remediate workloads — scan for deprecated/removed APIs (kubent, pluto); ensure availability during node draining (PDBs + topology spread, below); work the common workload checklist and the per-runtime cgroup v2 fixes (below).
  5. Phase 4 · Execute the rollout per environment — in each env, in order: control plane → add-ons → data plane; then clear the validation gate before promoting.
  6. Phase 5 · Post-upgrade — confirm versions, watch for OOMKills, redeploy Fargate workloads (they pick up the new version only on restart), update runbooks.

Availability during the node roll (PDBs + spread)

The data-plane upgrade drains nodes via the Eviction API, which respects PodDisruptionBudgets. A correct PDB keeps a quorum serving; a missing PDB risks an outage; an overly strict PDB (maxUnavailable: 0) blocks the roll with PodEvictionFailure.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: myapp }
spec:
  minAvailable: "80%"            # keep 80% of replicas up during voluntary disruption
  selector: { matchLabels: { app: myapp } }
---
# in the Deployment pod spec:
      topologySpreadConstraints:
        - maxSkew: 2
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector: { matchLabels: { app: myapp } }

cgroup v2 — per-runtime minimums (when moving to AL2023/Bottlerocket)

AL2023/Bottlerocket use cgroup v2. Older runtimes misread the container memory limit and size themselves from host RAM → OOMKilled at the same limits. Bump to:

Common workload checklist (all runtimes)

  • Deprecated/removed APIs migrated (Ingress, CronJob, PDB, HPA, RBAC, flowcontrol, etc.).
  • In-tree storage → CSI (EBS/EFS CSI drivers installed).
  • No Docker-socket dependency (Dockershim removed 1.24/1.25).
  • Resource requests/limits set (needed for cgroup v2 accounting).
  • PDB + topology spread on every user-facing Deployment/StatefulSet.
  • Accurate readiness/liveness probes; graceful SIGTERM + sane terminationGracePeriodSeconds.
  • Image tags pinned/re-pullable — nodes are replaced, so images must pull fresh.

Validation gate (run in EVERY environment before promoting)

✅ Control plane AND nodes report the target version.
✅ All nodes Ready; no OOMKilled / CrashLoopBackOff pods.
✅ Add-ons healthy (CoreDNS resolving, CNI assigning IPs, CSI mounting).
✅ No PodEvictionFailure during the node roll (PDBs held).
✅ Application smoke tests pass (auth, key endpoints, write paths).

KMS / encryption prerequisite (flag before you apply)

If a customer-managed KMS key encrypts EKS secrets, control-plane logs, or node EBS volumes, verify the key policy grants: CloudWatch Logs (logs.<region>.amazonaws.com) and the Auto Scaling service-linked role (key usage + kms:CreateGrant). Missing grants fail at apply time (not plan) — e.g. node launches loop with 0 instances. (This repo configures no KMS key.)

One minor at a time · Blue/Green alternative

1.31 → 1.32 → 1.33 → 1.34 → 1.35 → 1.36 → 1.37 — repeat Phases 2–5 for each hop; never batch minors. To reach 1.37 in one operational move, use Blue/Green: stand up a new cluster at the target version, deploy workloads, shift traffic, and retire the old cluster. Higher cost/effort but a clean cutover with instant rollback (shift traffic back). Control-plane in-place upgrades roll back within 7 days; after the data-plane roll they are effectively permanent — back up first.
