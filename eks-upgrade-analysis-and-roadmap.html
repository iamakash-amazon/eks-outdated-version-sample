Why upgrade

  • 1.24 is past the end of extended support (ended 2025-01-31). Amazon EKS automatically upgrades clusters on versions past extended support, so the live control plane has most likely already been moved forward and the Terraform no longer matches reality. EKS no longer accepts 1.24–1.30 for new clusters. [src: aws eks describe-cluster-versions --include-all, checked 2026-11-11]
  • 1.31 is the oldest version EKS still offers and is itself in extended support (per-cluster-hour surcharge); its extended support ends around 2026-11-26 VERIFY — keep moving forward quickly. [src: EKS extended-support versions]
  • Amazon Linux 2 retirement — 1.32 is the last version with EKS-optimized AL2 AMIs; from 1.33 nodes must run AL2023 or Bottlerocket. [src: EKS AL2 AMI deprecation notes]
  • Target 1.37 — recommended; end of standard support 2027-12-01. 1.36 is also supported for more than 180 days. [src: aws eks describe-cluster-versions]

Our recommendation

The repository is on 1.24. The target is the recommended version 1.37.

A — Reconcile to 1.31, then full sequence to 1.37 (6 in-place hops, validate between each). Reconcile the code to the version the control plane is actually on (1.31, the oldest EKS-offered version and where the automatic upgrade lands), then go one minor at a time. Recommended.

Roadmap to Production

Everything you need to take the transformed code safely to production is on this tab. EKS operates under a shared-responsibility model: AWS upgrades the control plane; you own the add-ons, the data plane, and validating that your workloads still run.

The upgrade order (and why)

  1. Assess readiness — Cluster Insights + deprecated-API scan. A removed API in use is rejected the moment the control plane advances.
  2. Fix the IaC (this transformation) — reviewable, repeatable across environments.
  3. Fix the workloads — API removals and OS/cgroup changes break apps, not infra. Remediate before the API server changes.
  4. Upgrade the control plane — AWS-managed, must lead the data plane.
  5. Upgrade the add-ons (VPC CNI, CoreDNS, kube-proxy, CSI) — NOT auto-upgraded; one minor at a time.
  6. Upgrade the data plane (nodes) to match — this is where AL2→AL2023 lands.
  7. Validate, then promote to the next environment.
ℹ️ Version-skew safety net: for Kubernetes ≥ 1.28, kubelet may trail the API server by up to 3 minor versions (n-3; n-2 below 1.28). A 1.24 node group under a 1.31 control plane is outside that window — upgrade the nodes as part of Step 0.

Phases

  1. Phase 0 · Plan & assess — run aws eks describe-cluster (control-plane version) and check node/kubelet versions; run Cluster Insights; read release notes; take a baseline/backup.
  2. Phase 1 · Set up a safe rollout path — Dev → UAT/Staging → Production; never upgrade prod first.
  3. Phase 2 · Upgrade the IaC — apply the reviewed diff; confirm the plan is in-place, not destroy/recreate.
  4. Phase 3 · Remediate workloads — scan for deprecated/removed APIs (kubent, pluto); PDBs + topology spread; cgroup v2 runtime fixes.
  5. Phase 4 · Execute the rollout per environment — control plane → add-ons → data plane; then clear the validation gate.
  6. Phase 5 · Post-upgrade — confirm versions, watch for OOMKills, redeploy Fargate workloads, update runbooks.

Availability during the node roll (PDBs + spread)

The node roll drains nodes via the Eviction API, which respects PodDisruptionBudgets. A missing PDB risks an outage; an overly strict PDB (maxUnavailable: 0) blocks the roll with PodEvictionFailure.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: myapp }
spec:
  minAvailable: "80%"
  selector: { matchLabels: { app: myapp } }
---
# in the Deployment pod spec:
      topologySpreadConstraints:
        - maxSkew: 2
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector: { matchLabels: { app: myapp } }

Common workload checklist

  • Deprecated/removed APIs migrated (CronJob, PDB, HPA, PSP→PSA, flowcontrol, etc.).
  • In-tree storage → CSI (EBS/EFS CSI drivers installed).
  • No Docker-socket dependency (Dockershim removed in 1.24).
  • Resource requests/limits set; PDB + topology spread on user-facing workloads.
  • Accurate probes; graceful SIGTERM; image tags pinned/re-pullable.

Validation gate (every environment, every hop)

✅ Control plane AND nodes report the target version.
✅ All nodes Ready; no OOMKilled / CrashLoopBackOff pods.
✅ Add-ons healthy (CoreDNS resolving, CNI assigning IPs, CSI mounting).
✅ No PodEvictionFailure during the node roll.
✅ Application smoke tests pass.

KMS / encryption prerequisite

No customer-managed KMS key is configured in this repo. If one is added for secrets, logs, or EBS, grant CloudWatch Logs and the Auto Scaling service-linked role (key usage + kms:CreateGrant) — missing grants fail at apply time.
